What happens when Dafny verifies a program

This page runs the verification pipeline in your browser and shows the intermediate artifact of each stage.

Dafny checks that a program meets its specification on every possible input. It does this by translating the program twice — first into the Boogie verification language, then into a logical formula — and asking the Z3 solver whether that formula can be violated. Each translation is mechanical, and each can be inspected below.

Stage 2 — Boogie: everything made explicit

Dafny first translates into Boogie, a small verification language. Nothing is proved yet — but everything implicit becomes explicit: the heap is a real variable, each specification clause becomes an assert or assume, definite-assignment and termination get bookkeeping variables, and every statement keeps a breadcrumb (/input.dfy(line,col)) pointing back at your source. Stage 3 — One formula per proof obligation

Boogie then compresses each method into a single logical formula — the verification condition — in SMT-LIB, the standard language of solvers. The trick to reading it: the formula states that some path through your method violates a claim, and it is handed to the solver negated — inside (assert (not …)). Stage 4 — The verdict

Z3 searches for an assignment that satisfies the formula — that is, for a concrete execution in which one of the claims fails. Two answers are possible:

unsat — the formula cannot be satisfied. There is no execution in which a claim fails, so the program is verified; unlike testing, this covers every input.
sat — the solver found such an execution. Dafny reads the solver's model back and presents it as a counterexample (the demo's Problems tab renders these).
